## #376: 待機しないフレームの保持領域

`Complete` を呼ぶのは Leaf と Then だけだった。結果と Fault を持つ `EffectFrame<T,E>` と、pending・Complete・WaitAsync を持つ `AwaitingEffectFrame<T,E>` に分け、Leaf / Then だけを後者から派生させる。Bind / Provide は子フレームを進めるため、pending を持たない。Then は非同期のエラー観測も扱うため、Map のためだけに待機領域を削除しない。

WaitAsync が呼ばれるのは Waiting のフレームだけで、Waiting を立てるのは待機可能な派生型の Complete だけである。不正な呼び出しは既定実装の例外で検出する。Complete / WaitAsync の本体、深さ予算64、文脈の捕捉・復元、失敗の採番、診断先、解放規則は変えない。共有プールは追加しない。

### 測定

同じマシン・Linux x64・SDK `11.0.100-rc.3.26522.148`・BenchmarkDotNet 0.15.8 の InProcess で、同じ ExecutorStorageBenchmarks を比較した。RunProvide を比較元にも追加し、返り値を既存の Setup で確認した。

最初の Short 3計測はばらつきが大きかったため、`DOTNET_TieredCompilation=0`、warmup20回・計測15回に揃えて、変更前→変更後と逆順の両方を測った。以下は最初の15計測の値であり、移植可能な上限ではない。

| 10万段・int / Never | 変更前の割り当て | 変更後の割り当て | 減少 |
|---|---:|---:|---:|
| Provide | 19,993,208 B | 13,597,368 B | 6,395,840 B |
| Map | 19,993,208 B | 19,993,208 B | 0 B |
| AndThen | 47,175,528 B | 40,779,688 B | 6,395,840 B |
| Resource | 100,445,064 B | 87,653,192 B | 12,791,872 B |

この型の ValueTask<Outcome> は64 Bで、対象フレームからその領域が外れる。T/E が変われば構造体のサイズも変わる。浅い経路は既存の割り当てテストで確認し、この InvocationCount=1 の表から小さい割り当てまで0と断定しない。

速度の平均は、Provide が2組とも約8.99 / 9.36 msから約5.73 / 5.91 msになった。一方、Resource は順方向で76.76→86.51 ms、逆順では92.85→78.56 msと傾向が反転した。AndThen の信頼区間も重なった。安定した成果は保持領域と割り当ての削減であり、全経路の速度向上や退行の不存在は主張しない。

再現例（変更前と変更後の独立した worktree で同じコマンドを実行する）：

```bash
DOTNET_TieredCompilation=0 dotnet run -c Release --project bench/Moderato.Effects.Benchmarks -- --filter '*ExecutorStorageBenchmarks.Run*' --inProcess --job Short --warmupCount 20 --iterationCount 15
```

全2,384テストと、同期・中断・再実行・同時実行・環境の回収を含む JIT の深い合成33ケースが成功した。最終コミットの package consumer と Native AOT も PR / CI の受け入れ確認に含める。

## #377: 継続運用

まず30分の実時間を使い、完了数・失敗数・解放の釣り合い、GC後ヒープ、割り当て、GC回数、スレッド／ハンドルを固定窓で記録する。完了済み環境は固定長の弱参照で確認し、診断用 List を無制限に溜めない。

ヒープの有限な増加だけでリークと断定せず、キャッシュや世代差、解放カウンタ、弱参照を併せて判定する。一定条件の有限試験であり、任意の業務負荷・無限時間の保証にはしない。実時間と件数を分けて残し、問題が見つかったら最適化とは別に最小の再現テストへ落とす。
