# 呼び出し側が所有する計算ノード領域

状態: #71 の設計検証。公開 API の採用案ではなく、D1–D18 は変更しない。

この方式を本体へ採用する場合、D1 の「不変の記述で、何度でも実行し直せる」という契約に、所有領域の世代内という寿命制限を加える必要がある。3型引数を保つだけでは互換性を維持したことにならない。また、ノードの事前確保だけでは非同期の継続登録に伴う割り当ては解消しない。これらは採用前に判断が必要な条件であり、この PR は設計変更を適用しない。

## 前提

作業セッションで、事前確保・容量・対応する非同期処理の規約を明示する方針を説明したところ、ユーザーから「であればいいですよ」、続いて「ユーザーがコントロール可能なのであればいいです」と返答を受けた。この確認は、呼び出し側が制御する事前確保方式を検証する根拠である。個別の Status、古いハンドルの無効化規約、既存 API の破壊的変更をすべて承認済みとするものではない。準備時の費用と実行時の費用を区別し、実行中の暗黙の容量拡張やプールへのフォールバックは行わない。

これにより、合成の型消去に必要なオブジェクトも準備時に確保する案を検討できる。型消去には毎回の割り当てが必須、という前提で公開型を4型引数へ変える必要はなくなった。今回の試作は、その選択肢を確かめるもの。

## 構成

- `Arena`: 領域全体の世代と、読み取り・書き込みの排他を保持する。
- 型別の `ConstantPool` / `MapPool` / `BindPool`: 準備時にノードを確保する。追加時は既存スロットを書き換え、容量不足は値で返す。
- `Computation<T,E,R>`: ノードへの参照と世代を持つ値型。ノードの具体型は公開ハンドルの型引数に含めない。
- ノード: 確保済みの参照型。インターフェースへの値型ボックス化を使わず、異なるノードを同じハンドル型で扱う。

`TryAdd` は新しい世代を始めない。既存のハンドルを有効にしたまま、その世代の未使用スロットを使う。`TryReset` は全ハンドルを無効化して参照を消し、スロットを再利用する。実行中のリセットとノード追加は拒否する。世代が尽きた場合も巻き戻さず拒否する。

同じ計算の再実行は可能だが、永続する計算の記述と、一回の非同期実行に必要な状態を同じ領域に混ぜてはならない。非同期実行領域は別の設計課題として残す。

## 試作で確認すること

```sh
dotnet run -c Release --project prototypes/Moderato.Effects.PreparedNodes
```

試作はライブラリ本体にも solution にも組み込まない。NuGet パッケージの対象でもない。

- 準備・ウォームアップ後に、定数と Map の構築・合成・同期実行が追加割り当てを生まないこと。
- ループで同じ型の変数へ計算を再代入できること。
- 定数ノードと Map ノードを同じ配列に保持できること。
- 値の型を変える Map と、Err の短絡。
- 容量不足を値で返し、すでに構築した計算を壊さないこと。
- 初期化されていないハンドル、リセット前の古いハンドル、別領域のハンドルを拒否すること。
- 実行中に呼ばれたリセットを拒否すること。

計測結果は PR に記録する。準備時・初回呼び出しの割り当てはこの試作の計測対象ではない。

## 互換性への影響

| 書き方 | 準備済みノード方式 | 構造体ノードを型引数に含める方式 |
| --- | --- | --- |
| 戻り値の型を明示 | 3型引数の形を保てる候補 | 具体ノード型か専用のノード定義が必要 |
| 同じ変数への再代入 | 同じ T/E/R なら表現できる | 合成後のノード型が変わる |
| 異種ノードの配列 | 同じ T/E/R のハンドル配列にできる | 型の統一か別の集合表現が必要 |
| 実行時に決まる合成回数 | 準備済みスロットの容量内で表現できる | 型の入れ子を実行時に増やせない |
| 領域の寿命 | 呼び出し側が管理する必要がある | 型付きの記述自体に領域の世代管理は不要 |
| 必要な準備 | 中間型と演算種別ごとのスロット確保 | 実行状態は別途必要だが、記述は値型で保持できる |

「3型引数を保てる」と「既存コードがそのまま動く」は異なる。現在の自由な構築には、領域の指定と容量不足の取り扱いが加わる。リセット後も有効な計算を返すコードは書けない。型ごとの準備をどれだけ簡潔に書けるかも未解決。

## 未検証・未対応

この試作をゼロアロケーション実行器として出荷してはならない。

- 同期の Bind は後述の形で検証した。中断可能な汎用 AndThen、LINQ、Never 変換、リソース、並行実行、付属失敗情報、時間・キャンセルは未実装。
- 非同期中断は、後述の固定した接続形と明示的進行だけを検証した。任意のグラフや通常の await への統合は未対応。
- 同期 Run のユーザー例外はそのまま投げる。明示的進行では例外の参照を Faulted として返すが、既存ライブラリの Die・スタック情報・キャンセル判定とは同等ではない。容量不足等を表す試作の Status も公開型ではない。
- 同期ノードを再帰で評価しており、深い合成のスタック安全性は未解決。
- 排他の自己テストは実行中の再入だけ。複数スレッドからの構築・リセット競合の安全性はまだ検証していない。
- Arena.Register と pool.Clear は試作の内部操作を直接露出している。準備後の登録や外部からの Clear を防ぐ製品用 API ではない。
- ウォームアップ後の測定だけで、初回、任意の中間型、全演算に対するゼロを証明したとは扱わない。

## 非同期側との関係

別の試作では、用意済みの結果ソースと継続を使う Map が中断し、同一スレッドまたは別スレッドから完了する経路で追加割り当てを避けられた。一方、Pending の確認と継続登録の間に入力が完了すると、標準の ManualResetValueTaskSourceCore によるキュー投入で割り当てが残った。

これはノードの表現とは独立した問題。任意の Task / ValueTask との接続まで、事前確保だけでゼロになるとは主張しない。[.NET の継続登録実装](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Threading/Tasks/Sources/ManualResetValueTaskSourceCore.cs)も、この競合で継続を非同期に送る経路を持つ。

同期 Bind と固定接続の中断実行を、以下の追加試作で検証した。次は任意の接続形に対する中断と、実行ごとの領域の渡し方を検証する。任意の外部非同期処理と接続する場合の保証範囲、結果の消費、容量不足時のリソース解放まで具体化してから、本体の公開 API を決める。


## 明示的に進める中断可能な実行

通常の await による消費まで含めて成立することを、今後の検証条件とする。手動 Advance の経路だけをゼロにし、await に接続した途端にライブラリ側の割り当てが戻る状態は、目標達成と扱わない。以下の Advance は、実行状態の保存と結果の所有権を切り分けて調べるための操作であり、最終 API を手動駆動だけに決めたものではない。

再開通知は単なる後付けではなく方式の成立条件である。次に、呼び出し側が準備・容量を制御する通知領域とスケジューラーで、登録前後の完了競合を扱いながら await を提供できるか検証する。任意の Task / ValueTask との接続、SynchronizationContext / ExecutionContext、キュー容量不足を含め、この確認なしに本体への採用判断をしない。

`PendingExecution<T,U,V,E,R>` を追加した。準備時に「同期の計算 → ValueTask を返す処理 → Map」という固定した接続形を指定し、実行状態は計算の Arena とは別のオブジェクトに保持する。これは汎用の AndThen ノードを実装したものではない。

1. `TryStart` は計算領域の読み取り権を取得し、実行の世代を返す。この時点では入力処理を呼ばない。
2. `Advance` が入力処理を一度だけ開始する。未完了なら Pending を返す。完了後の Advance で値を受け取り、Map を一度だけ実行する。
3. `TryTake` で結果を受け取ると、保持した参照と計算領域の読み取り権を解放する。それまでは別実行で上書きできない。

実行側で `OnCompleted` を登録しないため、先の継続登録競合を経由しない。試作の入力は、誤って継続登録すると失敗するようにしている。Pending と観測した直後に完了する入力、別スレッドで完了する入力も確認した。

測定は準備・ウォームアップ後の開始・進行・消費を対象にする。正常結果に加え、開始元の Err と中断した処理の Err の短絡を確認する。投げられた例外は参照が保持されることだけを検証し、例外経路の割り当てゼロは主張しない。別スレッド完了も挙動だけを検証し、そのケースの全スレッド割り当ては測定していない。

利用者は処理を進めるタイミングを制御できる一方、通常の await のように自動では再開しない。ライブラリは待機ループやスレッドプールへの投入を隠していない。呼び出し側のイベントループ等から Advance する必要があり、再開通知をどう受け取るかは未設計。入力自体が内部で作る Task や、入力ソースの GetStatus/GetResult が起こす割り当ては排除できない。

待機中・結果未取得のリセット拒否、古い実行世代、二重消費、Err 後に継続しないことを自己検証する。中断した実行の放棄・キャンセル・Dispose、終了時の解放処理はまだ実装していない。この試作では、開始した実行を完了まで進め、結果を受け取る必要がある。

固定接続の試作時点では、計算領域の読み取り権を保持すると TryAdd が Busy を返すため、継続の中で同じ領域に新しい計算を作れなかった。以下では、実行ごとの構築領域を分ける方法を検証した。同じ領域の未使用スロットへの並行追加は実装しない。


## 継続の中で組み立てる同期 Bind

`BindNode` は元の計算が成功した場合だけ継続を呼び、継続が返す計算を実行する。継続の戻り値 `BuildResult` は、構築が成功した場合の計算ハンドルと、容量不足などの構築失敗を分けて運ぶ試作用の値型である。これも公開 API の決定ではない。

継続は、元の計算領域とは別の scratch 領域で新しい計算を作る。返された計算はその所有領域の読み取り権を取得して実行するため、古い世代の参照は拒否される。元の計算は scratch のリセットで無効にならず、scratch を空にして同じ計算を再実行できる。使用中の元の領域へ追加しようとした場合は引き続き Busy を返す。

自己検証では、継続の遅延実行、実行ごとに継続を呼ぶこと、元と次の計算それぞれの Err、容量不足後も既存の計算が有効であること、古い継続結果の拒否を確認する。成功と容量不足を含む繰り返しの構築・実行を、準備とウォームアップ後に測定する。

さらに、同期 Bind を PendingExecution の開始元にして中断させる。Bind が返した同期計算の評価後は、その scratch 領域をリセットできる一方、元の計算領域は結果の消費までリセットできないことを確認する。これは中断可能な Bind ノードではなく、同期 Bind の後に固定接続の待機を行う試験である。

scratch の容量を消費するのは継続で新しい計算を作ったときであり、容量不足なら値として返す。自動拡張・自動リセット・スロットの暗黙回収はしない。呼び出し側は有効なハンドルが不要になった時点でリセットを選ぶ。

この試作では継続が scratch をクロージャに保持するため、同じ計算の同時実行にそれを共有する契約は未設計である。最終的には実行ごとの構築領域を明示的に渡す方法が必要であり、R のサービス依存に紛れ込ませることはここでは提案しない。中断をまたぐ scratch の保持、取得済みリソースがある場合の容量不足、結果としてハンドルが外へ返る場合の寿命も未解決として残す。
