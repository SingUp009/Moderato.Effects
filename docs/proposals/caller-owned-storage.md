# 呼び出し側が所有する結果領域と実行領域

状態: #213 の未採用の提案。公開する型・メソッドの決定や実装ではない。D1–D18 を変更しない。

2026-11-04 に、ローカル草案 `faf9a8e` を現在の実装 `22bbe10` と照合して更新した。今回の成果物は契約の比較・レビュー用の文書であり、試作や性能改善の完了を意味しない。#84 は閉じられた実現性調査の記録として残す。この提案で、その専用通知スレッドや準備済みハンドルを採用しない。

数学的な正しさと使いやすさを優先する。通常の await、自由に返せる計算の記述、同じ計算の並行実行を維持する。専用スケジューラー、手動の進行操作、4番目の Effect 型引数は要求しない。

この文書は全機能ゼロアロケーションの達成案ではない。結果領域について具体的な選択肢を示し、残る実行領域の問題を分離する。既存 API を保ったまま内部のプールを増やすだけで全面ゼロになる、とは扱わない。#84 の準備済みノード試作は比較資料として参照し、そこで未解決だった寿命・通知の問題を解決済みとしない。

## 3種類の寿命

| 対象 | 所有者と寿命 | 今回の扱い |
| --- | --- | --- |
| 計算の記述 | 利用者が保持・返却・再実行できる | Effect の寿命を実行領域のリセットに結び付けない。構築時の割り当ては残る |
| 実行状態 | 一回の実行。開始した子、解放、通知の完了まで必要 | 結果バッファとは別にする。再利用・容量の保証は未解決 |
| 結果 | 呼び出し側が実行後も保持できる | 既存 API の所有する結果と、任意で選ぶ借用バッファを区別する |

結果の配列を黙って使い回すと、以前の結果を保持するコードや同時実行に影響する。Scope、Fiber、CancellationToken の参照も、実行終了後に利用者側へ残りうる。内部状態を再利用できることと、これらの公開参照を安全に再利用できることは別である。

## 最初の具体案: コレクション結果への明示的な書き込み

一回の呼び出しごとに結果領域を渡す。計算の記述が特定のバッファを捕捉する形にはしない。以下は比較・レビュー用の未実装の書き方であり、そのままコンパイルできる利用例ではない。

```csharp
// The plan owns its input snapshot; construction may allocate.
AllPlan<Value, Error, Environment> plan = Effect.PlanAll(work, concurrency);

// The caller lends storage for this invocation only.
Memory<Value> destination = outputStorage;
BufferRun<Error> run = await plan.RunExitIntoAsync(env, destination, cancellationToken);

// Candidate discriminated value result; these APIs do not exist.
// Completed(Exit<int, Error>): Ok contains the written count.
// InsufficientCapacity(int required): no children were started.
```

`AllPlan` は不変の入力スナップショットを持つ記述とする。`default` は無効で、計画作成時に各 Effect を検証する。計画は自由に保持・返却でき、別々の出力領域を渡して同時に実行できる。

既存の `Effect.All` は所有する配列を返し続ける。比較案の `plan.AsEffect()` は同じ所有結果の意味を持ち、通常の Effect 合成に接続する。この接続では結果配列の割り当てをなくしたとは扱わない。バッファ版の戻り値が既存の `Effect<T[], E, R>` と同じ型になる、とは主張しない。

### 呼び出しの契約

1. 無効な計画の検査は、既存の `RunExitAsync` と同様に実行より先に行う。
2. 必要容量は入力数とする。容量不足なら値で返し、子・環境サービス・解放を開始せず、出力を変更しない。無効な計画の後、キャンセル状態より前に容量を検査する。
3. 容量が十分でトークンがすでにキャンセル済みなら、通常の Interrupted を返し、子を開始しない。
4. 通常の失敗順位、発生時点の分類、文脈の保持順、開始済みの子と解放を待つ規則を使う。
5. 全件が成功して後始末まで終わるまで、出力に書かない。Err・Die・Interrupted では出力を変更しない。成功時に入力順で先頭から必要数だけ書き込み、余りの領域は変更しない。
6. 完了結果を確定した後のコピー中には、新たなキャンセル判定を追加しない。後からのキャンセルで確定済みの結果を置き換えない。
7. 出力領域は呼び出し開始から非同期処理の完了まで借用する。通常は await で完了を確認する。キャンセルを要求しただけでは返却されない。
8. 呼び出し側は、その間の読み書き、重なる領域での別実行、メモリ所有者の破棄を行わない。ライブラリは所有権を受け取らず、Memory の所有者を Dispose しない。異なる Memory 値の背後にある重複領域を、ライブラリが自動検出すると約束しない。
9. 成功結果の公開前に Span を取得し、必要範囲を切り出して検証する。利用者の MemoryManager がそこで例外を投げた場合は、新しい Die として既存の失敗文脈を保ち、まだ書き込まない。不正な所有者によるメモリ破壊まで回復できる契約ではない。

借用の終了は、正常・失敗・キャンセルのいずれでも返された非同期操作の完了時とする。戻り値は件数と Exit のみを持ち、出力の借用ビューは保持しない。呼び出し側が完了後に領域を再利用すると、その領域を読む古いビューの内容も変わる。長く保持する結果には既存の所有配列版を使うか、呼び出し側でコピーする。

この借用の区切りは [.NET の Memory 利用指針](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines#rule-4-if-your-method-accepts-a-memoryt-and-returns-a-task-you-must-not-use-the-memoryt-instance-after-the-task-transitions-to-a-terminal-state)に合わせる。Span を await をまたいで保持せず、書き込み直前に一度取得する。非同期操作の完了後に、遅延 callback や診断が出力領域へ触れないことも契約に含む。

失敗時に出力を変更しないためには、子の値を一時的に保持する私有領域が必要になる。現在の ChildEnd 配列を使ってからコピーするだけでは、返却用配列の削減候補にはなっても内部配列の削減にはならない。借用領域へ逐次書き込む方式は部分書き込みの契約が異なるので、この案へ黙って置き換えない。正しく実装された MemoryManager と有効なメモリを前提に、取得・範囲検証後のコピーを途中で await しない。他スレッドからの不正な破棄や、壊れた MemoryManager に対して原子的な復旧は保証しない。

この方式は結果領域の所有を利用者へ移す。`All` の内部で必要な子の結果領域、キャンセル単位、並列 worker、非同期通知を消すわけではない。成功時の戻り値の配列を省けるかを、これらの費用と分けて評価する。

### 採用を見送る条件

- 通常の Effect 合成へ接続するために、利用者へ隠れたバッファの寿命制約を課す。
- 同じ計画を別領域で並行実行できない、または専用スケジューラーが必要になる。
- 普通の `Effect.All` を使うコードへ準備や容量管理を必須にする。
- 所有結果と借用結果の使い分けが、得られる削減に対して複雑すぎる。
- バッファだけを測定し、内部状態もゼロになったように説明する。

採用前に、直接の実行メソッドでは合成しにくい点を実際の利用例で評価する。`Memory<T>` を計算へ捕捉して見かけ上同じ型に戻すだけでは、再実行・並行実行時の所有の問題を解決したことにならない。

## AllErrors と AllSettled

同じバッファ型を無理に共用しない。

- `AllErrors` は値とエラーのどちらも最大入力数になる。両方の容量を実行前に確保する案では、どちらの領域の何件を有効とするかを表す結果型が必要になる。従来の `Err<E[]>` を残すとエラー配列の割り当てが残る。入力順、部分検証の中断、完了した集約を新しい失敗として扱う規則は維持する。
- `AllSettled` は `Memory<Exit<T,E>>` へ書けても、各 Exit に含まれる公開 Die などの参照型は別の割り当てである。結果配列を省くことと、失敗表現をゼロにすることを同一視しない。
- 容量不足を実行途中で知る方式では、すでに発生した副作用と解放を取り消せない。最初の検討は最悪時の容量を開始前に検査する方式とする。

この2つの最終的な戻り値の型は未決定である。All の試作が成立しただけで同じ形を採用しない。

## 合成の法則と観測の境界

比較する観測は、所有配列版と同じ値の並び、主の Exit、例外の同一性、付属情報の順序・Relation・省略件数、子の開始順と解放順とする。容量不足や出力所有者の例外は新しい境界であり、既存 API と同値とはしない。計算自体の Equals、内部の発生番号、実行時間の一致は同値性の根拠にしない。

借用先を持つのは終端の実行呼び出しだけとする。Map、AndThen、Provide、Retry、Repeat の計算記述や子の実行は呼び出し側の出力領域を捕捉しない。再試行中の一時的な成功や、後始末で失敗に変わった値を出力へ公開しない。所有配列を返す `AsEffect()` も別の境界であり、借用領域を隠して通常の Effect として合成する抜け道にはしない。

採用前の試作では、既存テストの成功だけでなく、次の法則を借用領域の再利用中にも確認する。

| 既存の検査 | 借用版で加える条件 |
| --- | --- |
| `AndThen_TotalBinders_AssociatesPublicExit` | 括り方が異なる計算の結果をそれぞれの領域へ出力し、値・実行順・Exit を比較する。結果領域は binder に渡さない |
| `AndThen_ContextCrossesRetentionLimit_AssociatesOrderedContext` | 100件の保持上限をまたぐ付属情報の順序と省略件数を保存する。失敗時は番兵で満たした出力を変更しない |
| `Retry_NestedFiniteSchedules_MultipliesAttemptCounts` | 同じ記述を複数回実行して出力領域を再利用する。試行回数と最終失敗を維持し、失敗した実行は前回の出力を変更しない |
| `Repeat_ZeroAdditionalRepeats_RunsOnceAndReturnsItsValue` | 呼び出しごとに一回だけ計算を実行し、新しい値だけを公開する。領域の再利用で前回値を返さない |
| `All_IndependentFailureDuringCleanup_RegroupingPreservesPrimaryAndClassification` | 同じ独立した失敗を平坦・入れ子の集約で比較し、主の欠陥と付属関係を保つ。後始末中の失敗で部分結果を書かない |

[CompositionLawsTests.cs](../../tests/Moderato.Effects.Tests/CompositionLawsTests.cs) と [CompositionBoundaryLawsTests.cs](../../tests/Moderato.Effects.Tests/CompositionBoundaryLawsTests.cs) が元の検査である。借用版は未実装なので、上表は合格済みの記録ではない。追加で、異なる領域を使う二つの同時実行、成功→失敗→成功での領域再利用、実行後も保持した通常の所有結果が後続実行で変わらないことを検査する。

## 全体目標に対して残る設計課題

| 領域 | この案の後にも残るもの | 成立を示すために必要なこと |
| --- | --- | --- |
| 一般の構築・合成 | Func とキャプチャ、実行中に AndThen が作る計算。反復実行器へ移行しても命令オブジェクトと束縛 delegate は残る | 自由に保持できる記述と通常の合成を維持した表現。領域リセットによる無効化を持ち込まない |
| 非同期の実行領域 | 待機したフレームの中断状態と継続登録、完了・登録の競合。#378 で待機しないフレームから待機領域を分離済み | 通常の await と既存のコンテキスト・スケジューラー規則を守った検証。入力処理自身の費用との分離 |
| Gen | Scope、実行の追跡、ScopeFailure | 古い Scope 参照が後の実行へアクセスできないこと。finally/using の巻き戻しと通常の async を維持すること |
| 並行処理・Fork | worker、Fiber、所有・終了待ち | 同一計算の並行実行、古い Fiber/Join の観測、放棄・キャンセル・解放を含む寿命の検証 |
| リソース・キャンセル | 解放登録、キャンセル単位、利用者の登録 | 容量不足でも登録済み解放を失わず、古いトークンや遅い callback が次の実行を壊さないこと |
| 時間・失敗の表現 | timer、実行ごとの乱数、dispatch 情報、公開失敗ケース、保持する文脈。保持操作は SuppressedContext へ共有化済みだが、公開 Die/Failed/Suppressed と保持配列は残る | 時間サービスと例外の意味を維持し、公開結果の保持期間まで含めて所有を説明すること |

実行領域を一つ渡せば上表が解決する、という設計にはしない。特に、既存の Gen に渡した同一 Scope オブジェクトを次の実行へ再使用すると、以前の実行が保存した参照と現在の参照を区別できない。世代番号を内部状態だけに置いても、両方の参照が同じオブジェクトを見るため解決しない。公開ハンドルを変えるか、実行ごとのハンドルを残す判断が必要である。

同様に、既存の不変な公開失敗オブジェクトや独立して保持できる結果を、有限の領域で無期限に増やし続けることはできない。事前確保の許可は、結果の保持期間やハンドル再利用規則への同意ではない。

## 検証と判断の順序

1. 製品の公開型を追加する前に、独立した試作で上の All の契約を確認する。既存の所有配列版と同じ入力を実行し、出力・失敗・キャンセル・解放の観測を比較する。
2. 0件、ちょうどの容量、過剰容量、不足、事前キャンセル、実行中キャンセル、Err、Die、解放失敗、MemoryManager の例外、同じ計画の再実行・別領域での同時実行を検査する。失敗時に既存出力が変わらないことを確認する。
3. 準備、初回、同期、未完了、全スレッド、失敗を分け、結果領域を省いた差と残る実行状態を記録する。計測値は PR に置く。プール命中だけを全経路ゼロとしない。
4. 利用例と測定を添えて、API の負担を採用してよいか判断する。成立しない場合は、この任意 API を出荷しない。
5. 実行領域は別途、容量不足時に開始済みの処理を安全に終える規則まで具体化して検証する。結果領域の試作だけで #64 や #71–#78 を完了にしない。

今回の判断対象は、借用結果という選択肢の契約と最初の試作範囲である。全機能ゼロの出荷時期、一般の構築がゼロになること、既存 API 全体を置き換えることは承認対象に含めない。
