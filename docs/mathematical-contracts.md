# 合成則と観測の範囲

この文書は、API のどの範囲にどの法則を適用できるかを定める。他ライブラリとの共通性だけで正しさを判断せず、型、評価、失敗、解放の契約を分けて確認する。有限個のテストが成功したことを、すべての C# プログラムに対する証明とは呼ばない。

## 参考にした資料

- ゆきくらげ、*Coeffect System — Effect の双対、Coeffect*（2025-06-14、提供された `Coeffect.pdf`）。特に pp. 13–19 の効果の合成、pp. 24–33 の文脈の使用量、pp. 39–49 の graded monad / comonad と合成。
- Gordon Plotkin / Matija Pretnar、*Handlers of Algebraic Effects*（提供された `Effect_Handlers.pdf`）。§2 の例外のモデル、§4 の正しいハンドラー、§6.8 の rollback、§7 の等式の適用条件。
- Matija Pretnar、*An Introduction to Algebraic Effects and Handlers*（MFPS 2015、提供された `handlers-tutorial.pdf`）。§3 の小ステップ意味論、§4 の型と効果、§5 の観測同値、§6.3–6.4 のモデルと等式。

式と推論規則は PDF のページ画像でも確認した。以下の API への対応付けは本ライブラリの設計判断であり、資料の定理がそのまま本実装を証明するという意味ではない。

## このライブラリが型で表すもの

`Effect<T, E, R>` は遅延された計算の記述である。`T` は成功値、`E` は期待内エラー、`R` は必要な環境を表す。実行時には、これらに加えて欠陥、キャンセル、解放、診断、.NET の実行コンテキストを扱う。

| 概念 | API との対応 | 保証の範囲 |
|---|---|---|
| 値と計算の区別 | `Succeed(value)` と `Sync` / `Async` | 引数の評価は通常の C# の呼び出し時、記述した仕事は実行時。binder の呼び出しも実行時 |
| 期待内エラー | `E`、`Fail`、`OrElse`、`Catch` | `E` は全副作用の集合ではない。I/O、状態変更、欠陥、キャンセルをすべて E が列挙するわけではない |
| 文脈への依存 | `R` と `IHas<T>` | 必要な能力を構造的な制約で表す。使用回数、線形性、機密度などの一般の graded coeffect を検査するものではない |
| 環境の変換 | `Provide` | 明示的な入力の反変な変換。任意の依存を動的に取り除く row polymorphism ではない |
| 操作と継続 | 内部の命令と実行ごとのフレーム | 中核の合成を駆動する閉じた実行器。任意の演算の宣言・捕捉・複数回の継続再開を公開する汎用の algebraic effect handler ではない |
| リソース | `Resource`、`Use`、`Acquire`、`Defer` | 取得成功を登録し、確定済みの ExitCase で逆順に解放する。任意の外部 I/O が自動的に rollback できるという主張ではない |

R を coeffect と呼ぶのは入力側の依存という対応付けである。`IHas<T>` を用意しただけで、資料にある指数付き comonad の構造やその法則をすべて実装したことにはならない。

## 法則を検証するモデル

逐次計算では、同じ入力・環境と制御された外部条件の下で、成功値／期待内エラー／欠陥／中断、実行された操作の順序、取得・解放の順序を比較する。欠陥は主例外の同一性と、付属情報の順序・省略件数も比較する。Effect のフィールド、Equals、内部フレーム数、失敗の採番そのものは計算の意味とはしない。

次の条件が必要になる。

1. 比較対象は有効な記述とする。default の Effect や、無効な子を返す binder は契約違反として別に検証する。
2. 等式で直接置換する記述の構築は純粋かつ全域的とする。binder を直接呼んでも、記述の構築時に例外、I/O、共有状態の変更が発生しないこと。binder が返す計算は実行時にログや状態変更を行ってよい。
3. 比較する計算の状態は明示的な環境や制御された入力に含める。AsyncLocal、SynchronizationContext、現在のスレッド、実時間など、ホストの await 境界や実行タイミングを観測する計算には、その追加の意味論が必要になる。
4. 時間切れやキャンセルとの競合を含む等式は、同じ引数の2実行が同じ結果だったことだけでは主張しない。制御した競合と起動・終了の規則を別に確認する。

この範囲では `Succeed` と `AndThen` の単位則・結合則、純粋な Map / MapErr の恒等則・合成則、独立した成功／失敗の写像の交換、純粋な Provide の合成を受け入れ条件とする。評価回数と順序も保ち、成功値だけが一致したものを同値とはしない。

`CompositionLawsTests` と `CompositionBoundaryLawsTests` がこれらを検証する。`HostContextLawBoundaryTests` は以下の適用外の例と、明示的な状態を使った対応する正の例を検証する。

## ホストの観測を含む場合

`Succeed(a).AndThen(f)` は f を実行時に呼ぶ。一方、C# の式 `f(a)` はその場で f を呼ぶ。f が構築時にカウンターを増やすなら、例外を投げなくても、その2つの構築のタイミングは同値ではない。「例外を投げない」だけでは左単位則の条件として足りない。

実際の待機を含む次の2式にも注意が必要になる。

```csharp
m.AndThen(f).AndThen(g)
m.AndThen(x => f(x).AndThen(g))
```

m が中断し、f の計算が AsyncLocal を変更し、g の計算がそれを読むと、外側の await が捕捉した文脈と、内側で続ける文脈は異なる。現行の .NET 境界を保つ実装では、同じ入力から左が0、右が7を返す例を再現できる。これは直接経路と反復経路の両方で確認する。

この観測を含む全 C# プログラムについて、無条件のモナド結合則を主張しない。違いを隠すために失敗したテストを除外するのでもなく、既存の async/await の文脈を変更するのでもない。業務上の状態を R のサービスや値として明示した対応例では、両式が同じ値と実行ログを返すことを確認する。AsyncLocal を使う既存の .NET ライブラリとの統合は、等式による括り直しではなく、実行コンテキストの契約とテストに従う。

## ハンドラー、並行処理、解放

資料のハンドラーは、返却値と操作に対する解釈を与える。解釈が選んだ等式を保つことには条件があり、正しい型を持つだけではその条件は証明されない。一般のハンドラーの順序変更や合成の結合則を、例外の単位則・結合則から自動的に導かない。

本ライブラリでも、OrElse / Retry が消費する失敗の診断、Race が選ぶ勝者、Timeout が変更するトークン、Use が確定するリソース寿命はそれぞれ意味を持つ。次の変換は一般則として採用しない。

- Timeout を AndThen や Use の内外へ移す。
- Race を括り直したり、引数の順序を入れ替えたりする。
- 回復処理を本体・子の計算・解放処理の間で移す。
- 解放順を変えた Resource を、利用時の値が同じという理由で同値とする。

代わりに、各操作の分類を成功・期待内エラー・欠陥・中断について全域的に定め、同期／非同期、逐次／並行の実装がその同じ分類に従うことを検証する。解放が Interrupted を返す Q13 の判断もこの全域性の問題であり、型名や他ライブラリの表面的な挙動だけで結論を選ばない。

## 変更時の確認

実行器や最適化を変えるときは、適用する等式とその条件を先に示す。結果、実行順序、短絡、失敗の保持、解放、実行コンテキストを確認し、その後で速度と割り当てを測る。数学的なモデル、.NET のホスト契約、測定による実装の証拠は互いに補完するが、同じものではない。
